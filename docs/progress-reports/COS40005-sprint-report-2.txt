Umer

Week 8 was focused on finishing the comparison algorithm and building the SQL generation
side. The scoring system in lib/compare.ts was fully built out: each table pair scored across four
dimensions with configurable weights (name similarity 20%, constraint family similarity 15%,
average pairwise column score 55%, FK graph neighbourhood 10%). Column-level scoring was
split into four sub-dimensions: name similarity using Levenshtein distance, type similarity with
separate handling for same-base-type versus full-type changes, constraint participation flags
(nullable, PK, unique, FK), and relative ordinal position. Similarity-based rename detection was
added so renamed tables and columns appear as candidates rather than being treated as a
deletion plus a new addition, which avoids generating a costly DROP and CREATE when a simpler
RENAME would do.
The SQL migration generator (lib/generate-sql.ts) was also built this week. The statement
ordering was the key design decision: table renames go first so subsequent statements
reference the right name, then CREATE TABLE for missing tables with FK constraints deferred,
then ALTER TABLE (column renames before ADD COLUMN, type and nullability changes after,
FKs dropped before any non-FK constraint changes and re-added at the end), and finally FK
constraints for the newly created tables. The GitHub push route was also wired up this week so
a script saved to the registry can be committed to the team repo directly from the UI without
switching tabs.

Week 9 was the most intensive week of the sprint. The script registry page
(app/scripts/page.tsx) was built from scratch: it groups scripts by script family name, shows
version history sorted by semantic version, infers change kind from the SQL content (breaking if
the SQL contains DROP TABLE/COLUMN, RENAME, or SET NOT NULL; additive if it contains

show family count, total versions, scripts flagged as breaking-looking, and the date of the latest
save.
The deploy panel was added to the same page. Users select a target connection, schema, and
script group, then click "Check DB" to run a pre-flight check, which queries the target database's
script_patch table for the current applied version and lists only the pending scripts (versions

strictly greater than the DB current) as a checklist. Scripts are applied in ascending version order,
with per-script status feedback updating in real time (idle, applying, done, error). The deploy
stops immediately on the first failure so no further scripts are applied on top of a broken state.
The script apply API route (app/api/scripts/apply/route.ts) was the most technically involved
piece this week. It wraps the submitted SQL in a full PostgreSQL transaction (BEGIN/COMMIT)
with ROLLBACK on failure. COMMIT/ROLLBACK injection in the submitted SQL is detected by
stripping line comments (--), block comments (/* */), and single-quoted string literals before
checking for the keywords, so something like INSERT INTO t VALUES ('ROLLBACK') is treated as
data rather than a statement. Duplicate version protection uses both a SELECT check before the
INSERT and a UNIQUE index on (script_name, version) to catch concurrent race conditions. The
script_patch audit table is auto-created and migrated with ADD COLUMN IF NOT EXISTS if it
does not exist or was created by an older app version. The admin control page was also finished
in collaboration with Meidy this week.

    4. RETROSPECT (CRITICAL REVIEW OF THE PROCESS)
Throughout Weeks 7 to 9, the team followed an iterative development approach to build the
core features of the Database Schema Comparison and Migration System. Work was organised
across three parallel streams: authentication and role management, database connection and
version management, and schema comparison with SQL migration tooling. Tasks were
distributed at the start of the sprint and reviewed during supervisor meetings and team check-
ins held as needed across the three weeks.

A clear strength this sprint was delivering all planned features to a working, demonstrable state.
The schema comparison engine, SQL migration generator, and transactional deploy pipeline
were all built and shown end-to-end in the supervisor demo. Database connection
management, credential testing, and version detection were completed and connected to the
frontend. Microsoft login via Azure AD and Supabase worked reliably by the demo session, and
the Admin Control page with role-based access was delivered as planned. The fact that three
independent workstreams converged into a coherent, working system by the end of Week 9 is
the most concrete evidence of the sprint's success.

Another strength was the willingness to dig into unfamiliar technical areas rather than take
shortcuts. Specific examples include studying PostgreSQL's pg_catalog system tables to write a
correct single-batch schema introspection query across all five constraint types, working
through the GitHub Contents API docs to implement push and pull directly from the app, and
tracing the Supabase OAuth session lifecycle to correctly diagnose the login redirect loop. These
were not quick lookups — each required real understanding of how the underlying systems
work, and the solutions that came out of that research are more reliable as a result.

Several challenges slowed progress during the sprint. The most disruptive was the infinite
redirect loop caused by a proxy.ts middleware intercepting the Microsoft OAuth callback URL
before the Supabase session cookie was set. Diagnosing this required tracing the full OAuth flow
and ultimately replacing the middleware approach with a client-side AuthGuard. On the
database side, writing a correct pg_constraint query — preserving column order through
LATERAL unnest and resolving referenced table names for FK constraints — required multiple

iterations and direct testing in pgAdmin before it was accurate. Team coordination also broke

From a cybersecurity and ethical perspective, several deliberate design decisions were made to
handle sensitive data responsibly. Database credentials are stored in environment variables via
.env.local and never committed to source control. The script apply API wraps all submitted SQL
in a PostgreSQL transaction with automatic rollback on failure, protecting target databases from
partial corruption. Role-based access control was implemented so only admin users can access
the Admin Control page or change user roles, preventing unauthorised privilege escalation.
Authentication is handled entirely through Supabase and Microsoft's OAuth provider, meaning
the application never stores or handles passwords directly. Australian Privacy Principles were
considered by limiting data collection to what is functionally necessary and by restricting
schema-level access based on assigned role. During all development and testing, only local and
development databases were used, ensuring no real production data was accessed. The one
acknowledged gap — plain-text storage of connection passwords in the local database — is a
known risk that will be addressed with encryption in Sprint 3.

For Sprint 2, the focus of our work was mainly divided into three areas – authentication and role
management, backend API and version detection, and schema comparison with script
deployment. Several key learnings were identified during Sprint 2.

Starting with authentication, integrating Azure AD with Supabase required very precise
configuration — any mistake in the redirect URI, optional claims configuration, or session cookie
timing breaks the login flow entirely. The infinite redirect loop from the proxy.ts middleware
was a direct result of route protection code running at the wrong point in the OAuth lifecycle.
Switching to a client-side AuthGuard that runs after the redirect completes fixed the issue
cleanly. The lesson is clear: any sprint that involves third-party auth or an external API setup
should treat that integration as a spike task to be started and completed on day one, with extra
buffer time allocated, before the rest of the sprint work begins. It should never be treated as a
standard implementation task slotted in mid-sprint.

From a backend perspective, we learned that it is crucial to validate database connection
management through our code. We implemented APIs for adding, fetching, modifying, and
deleting database connections, along with testing connections by validating user credentials
before storing. We discovered that PostgreSQL authentication failures, missing required tables,
and invalid API responses can cause major delays. Testing SQL queries directly in pgAdmin
before integrating them into APIs helps catch bugs earlier.

Team coordination was the weakest part of the sprint process. Without regular check-ins, each
member worked in their own lane for extended stretches without knowing what the others
were doing or what was blocked. This caused the workload to become uneven by Week 9 and
led to some integration issues being caught very late. A shared task board visible to all members
would have made task status transparent throughout the sprint and prevented most of the last-
minute pressure. For Sprint 3, a GitHub Projects board will be set up at the kickoff and updated
after each completed task.

Moreover, our environment variables cause issues. The database is stored locally, and each
team member may need different environment variables (different PostgreSQL passwords, port
numbers, or service names). Since .env.local files cannot be uploaded to GitHub, each member
needs to know exactly what variables to add to their own .env.local for the system to run
correctly.

Treat third-party OAuth integration as a sprint spike.
Setting up Azure AD with Supabase required understanding redirect URIs, optional claims, and
OAuth session cookie timing — all of which are easy to get wrong and very slow to debug. In
Sprint 2 this was treated as a normal task and consumed roughly twice its estimated time. For
any future sprint involving a third-party service, that setup should be the very first task of the
sprint, treated as a spike with extra buffer, and not considered done until it is working in a real
browser session before other work starts.


Test against realistic schemas, not just demo data.
The comparison algorithm and SQL generator were only tested against small, hand-crafted
schemas during Sprint 2. That was enough to demo but left real edge cases untested: circular FK
dependencies, schemas with a large number of tables, and unusual type casts. For Sprint 3, a
shared test schema closer to real client usage should be stored in the repository so all members
can run the same scenarios and catch regressions before the sprint review rather than
discovering them during the demo.
