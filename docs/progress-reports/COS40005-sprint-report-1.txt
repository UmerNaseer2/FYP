    4. RETROSPECT (CRITICAL REVIEW OF THE PROCESS)

During the sprint, the team followed a simple workflow using physical meetings, Microsoft
Teams, and WhatsApp for communication. Tasks were divided among members based on roles,
with frontend and backend handled separately. GitHub was used to manage code and track
progress. Overall, the team maintained consistent communication, which helped ensure that
everyone was aligned with the project goals.

One of the main strengths of the team was effective communication and collaboration. Meetings
with the client and supervisor provided clear guidance, while task distribution allowed members
to focus on their responsibilities. However, the team faced some challenges, including unclear
requirements in the early stage and technical issues such as routing errors, JSX syntax errors, and
layout problems during frontend development. These issues were resolved through discussions,
debugging, and applying feedback from the supervisor.

The team followed a basic code of conduct by respecting each member, completing assigned
tasks on time, and communicating any issues early. In terms of cybersecurity and ethics, the
project ensured that sensitive data such as login credentials and database details were handled
carefully. Basic principles similar to the Australian Privacy Principles were considered, including
protecting user data and limiting access. Only sample data was used during development and
testing to ensure privacy and security.




    5. LESSONS LEARNED (CRITICAL REVIEW OF SPRINT ONE EXPERIENCE
        AND FUTURE PLAN)

During this sprint, we learned a lot from trying to build both the frontend prototype and the
backend comparison logic at the same time. The main lesson was that even if the idea sounds
simple at first, a schema comparison system has a lot of detail once we actually start
implementing it. On the frontend side, it was not enough to just create pages and navigation. The
screens only became meaningful once the backend could return real comparison results. On the
backend side, it was not enough to just connect to PostgreSQL. We also had to work out how to
read schema metadata properly and compare tables, columns, and constraints in a way that was
actually useful.

The other major lesson was that we should have confirmed the technical setup with the client
earlier. At the beginning, we considered Supabase as the backend because it seemed like a quick
way to start development. Later, after discussion with the supervisor, we found that the client
wanted the system to run locally on a computer. Because of that, we had to change direction and
rebuild the backend around local PostgreSQL. That change taught us that technical decisions such
as hosting, environment, and database setup need to be confirmed early, because they affect both
frontend integration and backend development time.

We also learned that frontend and backend work cannot be treated as completely separate. During
this sprint, the frontend pages helped us visualise the system, but the compare page only became a
proper feature once the backend could return structured data such as tables only in A, tables only
in B, matched tables, column differences, and constraint differences. This showed us that the
interface and the backend logic need to be planned together, especially for a feature like schema
comparison where the output structure is important.

Another lesson was about testing. For the backend, we found that comparison logic can look
correct on paper but still fail in real cases, especially with renamed columns, constraint matching,
and schema edge cases. For the frontend, we also saw that a page may look fine visually but still
not communicate the results clearly enough for a demo. This sprint showed us that we need to test
not only whether the system works, but also whether the output is understandable to the user.

Lessons we learned in this sprint:

    •   We need to confirm the required environment earlier, especially whether the system must
        run locally or can depend on a cloud backend.
    •   A frontend prototype is useful, but it can only show real value once it is connected to
        actual backend logic.
    •   Schema comparison is more detailed than expected because it involves tables, columns,
        data types, nullability, order, and multiple kinds of constraints.
    •   Backend logic needs regular testing with realistic schema examples, not just one simple
        case.
    •   Frontend design for a report-style page needs to focus on clarity, because too much
        empty space or unclear wording can weaken the demo even if the backend is correct.
    •   Team coordination matters more when one part of the group is building interface screens
        and another part is building the logic behind them.

    •   For the next sprint, our recommendations are:
    •   Finalise technical decisions earlier before spending too much time on one backend
        approach.
    •   Improve coordination between frontend and backend so that the data returned by the
        backend directly supports what needs to be shown in the UI.
    •   Prepare better sample databases earlier so both the algorithm and the report page can be
        tested properly.
    •   Continue improving the schema comparison feature, especially its reliability and clarity
        for demonstration.
    •   Spend more time polishing the report output so the frontend presents the backend results
        more clearly.
    •   Keep documenting changes as we go, so writing reports and explaining progress is easier
        at the end of the sprint.

Overall, this sprint taught us that building the system was not just about dividing frontend and
backend tasks. The main challenge was making both parts support each other properly so the
project moved from a simple prototype into something that could actually demonstrate the core
schema comparison feature.
