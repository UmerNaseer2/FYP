The problem which I resolved during Week 10 was that the application could not read the user
role from the profiles table. There might be the correct roles (either admin or viewer) in the
table, but either there were no RLS policies set up or they were implemented in a wrong way.
This was making the useUser hook always return the 'viewer' role and the Admin Control page
not to show any users.

Firstly, I turned off the RLS policy temporarily to check whether the data itself is valid. Then after
checking that role values are indeed correct, I dropped all the incorrect policies and used a
different approach to solve the problem. I created a SECURITY DEFINER function called
get_my_role(), which works with database owner privileges, thus ignoring RLS, and which
returns the role of a particular user using auth.uid(). Having done that, I enabled the RLS again
and introduced two new policies, Users can view their own profile, and Admins can view all
profiles.

With these changes, the application could determine whether the user was an admin or a
viewer and display all users on the Admin Control page.

   3. SPRINT REVIEW
The Sprint 3 increment was demonstrated to the client and supervisor, Jason Thomas Chew,
during the Week 12 meeting. The session walked through the full end to end flow of the tool
running on the live Vercel deployment, starting from logging in through Microsoft Entra ID and
ending with a generated migration script pushed to GitHub. The goal of the demonstration was
to show that the tool now works as a hosted, access controlled application that the whole team
and the client can reach from the same place, rather than something that only runs on one
person's machine, and to collect the client's feedback on what to prioritise next.

What was demonstrated:

   •      Logging in to the deployed application through Microsoft Entra ID, with the app
          enforcing the login before any page can be reached.
   •      The schema comparison report, showing both table level and column level differences
          between two databases (A against B).
   •      Migration script generation with the changes grouped by severity (breaking, safe or
          additive, and informational), including the new DROP TABLE and DROP COLUMN
          handling.
   •      Saving a generated script to the script registry and pushing it to GitHub.
   •      Drift detection, tracking how a schema has changed against a captured baseline over
          time.

                                                                        PORTFOLIO TASK 2/3/4

    •   Version Sync, replaying the scripts a target schema is missing so it can be brought back
        in line with a source schema.
    •   The Schema Visualizer, rendering a schema as an interactive ER diagram, including the
        side by side mode for comparing two schemas at once.
    •   The Connections page, adding, editing and testing a saved database connection with the
        SSL toggle.
        Client feedback
        The client treated the demonstration as a working prototype and gave the following
        feedback for the next increment:
    •   Single source of truth for scripts. Scripts are currently stored in two places, the local
        script table and GitHub, which risks the two drifting apart. The client recommended
        making GitHub the single source of truth and adding a sync button so the local table
        always matches the remote repository.
    •   Rollback support. There are no downgrade scripts yet. The client said every upgrade
        script should ship with a matching downgrade script, following a proper migration
        pattern, so a bad change can be cleanly reversed.
    •   Change preview before running. The tool runs a script without first showing what it will
        change. The client asked for a summary or a visual diff so the user can review the impact
        before anything executes.
    •   Local database connectivity. The hosted web app cannot reach databases running on
        localhost and only works with online databases such as Neon and Supabase. The client
        noted this as a genuine limitation for real world use that the team should be upfront
        about.
    •   Support for concurrent development. With more than one person working on the same
        schema, the client suggested leaning on GitHub as the central history so the team can
        manage parallel changes without overwriting each other.
        Progress against the sprint plan


The sprint goal was to move the tool from a local prototype into a deployable, access controlled
increment, and that goal was met. The team delivered the authentication migration and login
enforcement, the deployment to Vercel against online databases, and the full compare,
generate and push flow working end to end, on top of the new Drift Detection, Version Sync,
Schema Visualizer and Script Editor modules. Four items did not make it into this sprint and
were carried into Sprint 4: rollback and downgrade scripts, making GitHub the single source of
truth, the script change preview, and password encryption for stored connections. It is worth
noting that all four of these line up directly with the feedback the client raised in the
demonstration, so the next sprint follows on logically from this review rather than starting from
a fresh set of priorities.

The client was satisfied with the progress made over Sprint 3 and was comfortable with the
team carrying the remaining items into FYP B.

   5. LESSONS LEARNED (CRITICAL REVIEW OF SPRINT THREE EXPERIENCE AND FUTURE
      PLAN)


Sprint 3 was different from the earlier sprints because most of the work was building on
top of features that already existed rather than starting from nothing. That sounds easier,
but it actually brought its own set of problems, and we learned a few things the hard way.

The biggest lesson was that integration should happen early and often, not at the end. A
lot of the new work this sprint, like Drift Detection, the Schema Visualizer and Version
Sync, was developed in separate branches and only really tested together near the end of
the sprint. When we finally merged everything, we ran into compatibility issues and a
few bugs that only showed up once the frontend was talking to the live backend APIs. If
we had merged smaller pieces more frequently, most of those issues would have been
caught while they were still small and easy to fix.

Related to that, we learned that our GitHub workflow needed to be tighter. Because
several people were touching the same areas of the codebase, we ended up with merge
conflicts that took real time to sort out, and at one point we had to be careful that new
features were not quietly breaking things that already worked. Back in Sprint 2 we said
we would use a shared task board and do regular check-ins, and we did improve on this,
but we still did not stick to it as consistently as we should have. When everyone knows
what the others are working on, it is much easier to avoid two people editing the same file
at the same time.

Testing was another area we underestimated again. Even though we added test cases for
the comparison and version logic this sprint, a lot of problems still only became obvious
once the full system was running end to end. Things that looked fine in isolation behaved
differently once they were connected to real data and the other modules. This told us that
unit tests are useful but they are not enough on their own, and we need to spend proper
time testing the whole flow before a demo, not the night before.

On the positive side, the studio rebuild and the move to a shared set of UI components
made development noticeably faster once it was done. Having one consistent layout and
reusable pieces meant new screens like the Visualizer and Version Sync took less time to
put together and looked consistent without extra effort. That was a good reminder that
spending time on the foundation early pays off later, even if it does not feel like visible
progress at the time.

We also kept the security and ethics side in mind throughout the sprint. Database
credentials and sensitive details were kept out of the public repository, and access control
was used to stop unauthorised users from reaching parts of the system they should not.
Since the project deals with database connection information, we only tested against our

                                                                       UNIT CODE COS40005
                                                                      PORTFOLIO TASK 2/3/4
                                                                               PAGE 20
own local and online development databases, such as Neon and Supabase and did not
touch any real or personal data.

Recommendations to carry into the next sprint:

   •   Merge and integrate small changes regularly instead of leaving it until the end of
       the sprint.

   •   Actually keep the task board updated and hold short check-ins, since the times we
       did this it clearly helped.

   •   Agree on simple GitHub habits (pull before you start, smaller pull requests, clear
       commit messages) to cut down merge conflicts.

   •   Write tests as features are built, and always run a full end to end test of the system
       before any demo.

   •   Keep documenting features as we go so the report and the handover are not a
       scramble at the end.

   •   Continue being careful with database credentials and user permissions as the
       system gets closer to something that could actually be deployed.

Overall, Sprint 3 showed us that building on an existing system needs just as much
planning as starting one, especially around integration, testing and keeping the team in
sync. The features we delivered worked, but the process taught us where we still lose
time, and most of that comes down to merging late and testing late.
