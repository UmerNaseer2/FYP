1. OVERVIEW
================================================================================

Schema Studio is a web-based tool for PostgreSQL schema management. It lets you:

  • Compare schemas between databases (dev, staging, prod) and generate migration
    SQL to bring them into sync
  • Version-control schema migrations with a ledger system (script_patch)
  • Replay missed versions from one schema to another (catch-up sync)
  • Visualize table relationships and foreign keys as interactive diagrams
  • Track schema drift over time (unintended divergence from a baseline)
  • Find what a schema is likely to be slow at, and analyse individual queries
  • Safely apply and audit all schema changes

All work belongs to an organization. Each organization has its own people,
roles, saved connections and scripts, and its address is the first part of the
address of every screen. Inside it you can have multiple PostgreSQL connections
(dev, staging, production) and compare/sync between any two.

AI assistance is optional. It can summarise a comparison, review a run before
you deploy it, explain a drift, draft SQL from plain words and answer
questions about a schema. It is off until an admin switches it on (see THE AI
TAB in section 11).

This manual covers the website. The desktop app and the phone app have their
own guides in the project: desktop/README.md and relay/README.md.

2. GETTING STARTED
================================================================================

LOGIN
-----
Schema Studio signs you in with an account you already have: a Microsoft
account (Microsoft Entra ID, which used to be called Azure AD) or a GitHub
account. The login page shows a button for each one the server is set up for.

SIGN IN FLOW
  1. Open the site. The first page has two buttons, "Create account" and
     "Log in". Both take you to the login page.
  2. Click "Continue with Microsoft" or "Continue with GitHub"
  3. Sign in on that service's own page. Complete multi-factor authentication
     if prompted.
  4. You come back signed in. If you already belong to an organization, you
     land on its Dashboard.

If the server you're using has no sign-in keys at all, the login page says
"Single sign-on is not set up." and names the values the server needs. The
Microsoft button is shown switched off, rather than failing when you press it.
Ask whoever set the server up; the values are also listed in the project
README. "Trouble signing in?" under the buttons opens a short help text.

YOUR FIRST ORGANIZATION
-----------------------
Someone who is not in any organization yet lands on "Your organizations",
which says "You are not in any organization yet." There are two ways on:
  • Join one. If someone sent you an invitation link, open it. The page is
    titled "Join" and the organization's name. Press "Join".
  • Create one. Under "New organization", type a Name. The Address is the part
    of the web address its pages open at. "Connect GitHub (optional)" takes
    the Repository and Access token where the organization's scripts will be
    kept. You can leave it and add it later on the Admin screen, under GitHub.
    Press "Create organization". You will be its Admin, and can invite others
    from it.

Once you are in an organization, you have a role in it. Three are built in:
  • Viewer: starts able to open every screen except Admin (compare, visualise,
    review) and to change nothing
  • Editor: starts able to change things too, and to run migrations on the
    connections that allow it (see "Who may run migrations here" under
    Connections)
  • Admin: can do everything, always. Only Admin can change what a role may
    do or run the organization itself

"Starts able to", because an admin decides what each role may do, feature by
feature, and can make new roles as well (section 11). The server checks your
role on every request, not only the screens. A button your role can't use is
switched off or left out, and anything it is not allowed to do is turned down
with a message that names the permission an admin would need to turn on, for
example:

    Your role (Viewer) can't add a connection. Ask an admin to turn on
    "Add a connection" for this role.

The name in quotes is a line on Admin > Roles & permissions ("Add a
connection" sits under Connections), so an admin can find it straight away.
Section 11 lists every line.

Your role, and whether you got it by signing in at all, are shown in the
bottom-left of the sidebar under your name. See SETTINGS in section 12.

DASHBOARD
---------
After login, you land on your organization's Dashboard. Here you can:
  • See all tracked schemas at a glance
  • View drift status (schemas vs. their baseline snapshot)
  • Open a schema card to see its history of versions and its drift
  • Stop tracking schemas you no longer need to monitor

3. CONNECTIONS
================================================================================

A "Connection" is a saved PostgreSQL database you want to compare or monitor.

ADDING A CONNECTION
-------------------
  1. Go to Connections (left sidebar > Connections)
  2. Click "Add connection" (on an empty list the button reads "Add your
     first connection"). A drawer titled "Add connection" opens. Under "Quick
     start", "Local Postgres" and "Hosted (Neon · Supabase · RDS)" fill in a
     name and the SSL mode each one needs.
  3. Give it a "Friendly name", for example "production", "staging" or
     "dev local"
  4. Set the Environment: Unlabelled, Dev, Staging or Production. You can also
     tick "Mark as production". This is only a label, but it is the label that
     drives the production warnings and the approval you'll meet before a
     deploy, so it is worth setting.
  5. Enter the connection details, either way round:
     • Connection string: paste a postgres:// URI
     • Fields: Host, Port (usually 5432), Database, User, Password
  6. Pick the SSL mode:
     • Off — no encryption. Normal for a localhost loopback connection.
     • Require — encrypts the link but accepts whatever certificate the server
       presents. This is what hosted Postgres (Supabase, Neon, RDS) needs.
     • Verify full — also checks the certificate chain and hostname. Fails
       against a self-signed certificate.
  7. Choose who may run migrations here:
     • Anyone whose role may run deployments (the default)
     • Admins only: people with the Admin role itself. A role an admin made
       does not count, whatever it is allowed to do.
     • Read-only: nobody may run migrations here, admins included
     This is checked by Deploy, by Revert and by a Version Sync replay, on top
     of the "Apply or revert migrations" permission (section 11).
     It can only narrow who may run migrations here, never let anyone else
     in. Anyone who may edit the connection can make it stricter. Making
     it looser again (read-only to anything else, or admins only back to
     the default) needs "Approve production runs", which out of the box
     only an Admin has. Comparing, generating scripts, previewing and exporting are
     unaffected by it: it only decides who may make this app WRITE to this
     database. A reference or model schema you never want written to is the
     read-only case.
  8. Optionally name an Application table — a table on this database with an
     `application_name` column. Deploy reads it to decide whether a script
     marked `-- Applies-to: billing` may run here.
  9. Under "Test connection", click "Test now" to verify the connection works.
     Then click "Save connection" at the bottom of the drawer ("Cancel" closes
     it without saving).

Once saved, the connection is listed in a table. You can:
  • Test it again with "Test" on its row (verify credentials are still valid)
  • View its last-tested timestamp
  • Edit it with "Edit" on its row, including its environment label. The
    drawer's button then reads "Save changes". A schema you track through
    this connection inherits that label when you start tracking it, and can be
    relabelled afterwards on its own detail page.
  • Tick "Group by environment", or filter the list (All, Local, Remote,
    SSL on)
  • Delete it (removes it from the app, not the actual database). It asks you
    to confirm first.

Each of these is its own permission: "Add a connection", "Edit or test a saved
connection" and "Delete a connection". Out of the box Editor and Admin have all
three. A role without one still sees the button, switched off, and the page says
why once, under its header.

IMPORTANT: Passwords are encrypted at rest and never shown after saving.

LINKING A COMPUTER
------------------
The desktop app can be linked to an organization on the website. A linked
computer gets the organization's saved connections, and the connections kept
only on that computer are listed here by name (their passwords stay on it).

  1. On the computer, open Schema Studio's Settings, enter the site's address
     and click "Link". The app shows a code of eight letters and numbers, and
     your web browser opens the site's "Link a computer" page.
  2. Sign in if the site asks you to.
  3. Type the code under "Code shown on the computer". The address of the
     page never fills it in, so you always read it off the computer in front
     of you. Only link a computer you are sitting at, and never type a code
     that someone sent you.
  4. Read what the page says before you go on: linking lets that computer
     open the organization's saved connections, including their passwords,
     and answer questions from your account.
  5. If you belong to more than one organization, pick the right one under
     "Organization".
  6. The page names the computer and says when it asked. Click "Link this
     computer", or "Not mine" if you did not start this just now.

A code works for 10 minutes. Linking needs a role that may compare schemas.

Linked computers are listed on the Connections page under "On linked
computers". An Admin sees every linked computer there and can unlink any of
them with "Unlink", for instance one that was lost. Everyone else sees the
computers that hold connections of their own, and can unlink their own one.
A computer can also be unlinked from its own Settings.

A link ends by itself when the computer has not been used with the site for
90 days. Link it again the same way: it takes a minute.

4. DASHBOARD
================================================================================

The Dashboard shows all schemas you've tracked and their current state.

TRACKING A SCHEMA
-----------------
  1. Go to Dashboard
  2. Click "Track a schema". A dialog with the same title opens.
  3. Pick a Connection ("Select a connection…")
  4. The app reads that database and lists its schemas. Pick a Schema
     ("Select a schema…").
  5. The Environment starts as the connection's ("Inherited from the
     connection"). Change it if this schema is a different one ("Set for this
     schema"). You can also type a "Label (optional)".
  6. Click "Track schema" ("Cancel" closes the dialog). A baseline snapshot is
     taken straight away and recorded as version v1.0.0.

Once tracked, the schema appears as a card showing:
  • Schema name, its connection and database, and its label if it has one
  • Drift status: Drifted, In sync, Unreachable or Not checked
  • Its environment
  • Its lineage version. This is Schema Studio's own counter for the tracked
    schema. It is separate from the script versions that Deploy shows.
  • What the last drift check found, or "No drift check yet."

Each card has buttons: "Open", "Check drift", "Compare", a button to stop
tracking, and "Review drift" when the schema has drifted. Above the cards,
"Refresh" reads the list again, and the filter chips (All, Production,
Drifted, In sync, Unreachable, Not checked) narrow it.

VIEWING SCHEMA DETAILS
---------------------
Click "Open" on a schema card to open its detail page. You'll see:
  • Its drift state, with "Check drift now" (or "Re-check drift"), and
    "Review drift" when it has drifted
  • Counts of what is in the schema, taken from its newest snapshot
  • Its environment, which you can change here
  • Lineage: the history of its versions, each with its snapshot and its
    migration script where one is stored
  • "Compare with another database", which opens Compare with this schema as
    the target

DRIFT DETECTION
---------------
Schema Studio takes a snapshot of each tracked schema when you first track it.
The "drift" status compares the live database against the stored baseline
snapshot. A check runs when you press "Check drift", after each deploy, and on
its own if the schema has a schedule (Drift > Schedule, section 8).

If drift is detected, click "Review drift" or go to Drift to see:
  • Tables added or dropped
  • Columns added, renamed, or dropped
  • Type or constraint changes
  • When the drift was first detected

Note: Drift is informational. It doesn't auto-correct anything.

UNTRACKING A SCHEMA
-------------------
On a schema card, click the stop tracking button. A dialog asks "Stop tracking
this schema?". Press "Stop tracking" to confirm. This removes the schema from
your dashboard and deletes its baseline snapshot. The database itself is not
touched.

5. COMPARE & AUTHOR
================================================================================

Compare two schemas and generate migration SQL to sync them.

STARTING A COMPARISON
---------------------
  1. Go to Compare (left sidebar > Compare & Author)
  2. Pick two schemas, each as a connection and a schema:
     • "Source · the schema you want"
     • "Target · the schema that gets updated"
  3. Optionally click "Add target" to compare the same source with more
     targets, up to six. Each target is compared with the source only, not
     with the other targets. "Use as source" on a target swaps it with the
     source.
  4. Set the two switches if you need them:
     • "Allow data loss": while it is off, statements that would delete data
       (DROP TABLE, DROP COLUMN) are written into the script commented out
     • "Compare row data": also reads the rows of every table and reports
       which ones differ. Much slower on big tables.
  5. Click "Compare"

The app will:
  • Introspect both schemas
  • Find differences
  • Show a report of them, and a generated migration, for each target

Comparing changes nothing in either database.

The "Saved sets" bar at the top keeps a source and its targets under a name,
so you can open the same comparison again later ("Open a saved set…").

READING THE DIFF
----------------
Each target's result has:
  • A "Summary" table with one row for every kind of object and four columns:
    In sync, Only in source, Only in target and Changed
  • The report itself, grouped by kind: tables (columns, primary key, foreign
    keys, other constraints, indexes, triggers, row security, partitioning),
    views, sequences, types, extensions, collations, functions, and ownership
    and grants
  • "Export this diff": Copy as Markdown, JSON, CSV, or Print / PDF

A renamed table or column is written as a rename only when its structure
matches and the two names are very close. Otherwise the report offers it as a
rename to confirm by hand, and until then the script creates the new one and
drops the old one. That drop deletes data, so it stays commented out while
"Allow data loss" is off.

Foreign key changes are also shown. Note: cross-schema FKs may report spurious
changes due to schema-prefix differences in the comparison.

If AI assistance is on (section 11), a "Change summary" panel has a
"Summarize with AI" button that explains the differences in plain words.

GENERATING MIGRATION SQL
------------------------
There is no button to press: every target's result already has a "Generated
migration" panel under its report.
  1. The "Migration" tab holds the script that makes the target match the
     source. The "Rollback" tab holds the script that undoes it.
  2. The script is written in dependency order. In short: extensions,
     collations, types and sequences first, then new tables, then changes to
     tables that exist on both sides, then dropped tables, then indexes,
     foreign keys, triggers, row security and views, then ownership and
     grants. Things that are no longer used are dropped last.
  3. The SQL respects PostgreSQL's dependency order (you can't drop a table
     if another table references it with a foreign key)

REVIEWING & CUSTOMIZING
-----------------------
The generated SQL is fully editable, on both tabs. You can:
  • Delete steps you don't want to apply
  • Reorder steps (be careful of dependencies)
  • Add your own SQL (e.g., data migrations, index creation)
  • Add comments for clarity
"Reset" puts the generated script back and "Copy" copies it. Do not write
BEGIN, COMMIT or ROLLBACK in a script: Deploy wraps the whole run in one
transaction, and the panel refuses to push a script that has them.

SAVING THE MIGRATION
--------------------
Compare never runs the script. It saves it to your organization's script
registry on GitHub, and Deploy runs it from there (section 10).
  1. Check the "Migration name" (this is the script group the version belongs
     to) and type a "Description" if you want one
  2. Under "Change level", pick breaking, additive or patch. "Next version"
     shows the version number that level gives.
  3. A version is saved with its rollback. To save one without it, tick the
     box that starts "Save without a rollback". Deploy will then not be able
     to undo that version.
  4. Click the push button. It reads "Push to GitHub", with the version number
     in it once that is known.
  5. When it has saved, "View on GitHub" opens the file, and the link that
     starts "Nothing has run yet" takes you to Deploy.

Saving needs "Save scripts to the registry", and a GitHub repository set up
for the organization (Admin > GitHub, section 11).

After a successful deploy (section 10):
  • The script_patch table (on that schema) is updated with a new ledger entry
  • The script's SQL is stored for future version replay
  • The version shows as applied on Deploy and on Version Sync

6. SCRIPT EDITOR & VERSION SYNC
================================================================================

Version Sync lets you manage a ledger of applied migrations per schema and
replay missed versions to catch one schema up to another.

SCRIPT EDITOR
-------------
Go to Script Editor (left sidebar). The page is headed "Write a migration
script." It is where you write a migration by hand and save it to the GitHub
registry. Nothing runs against a database from this page: running is Deploy's
job (section 10).

  1. Under "Where this script belongs", pick a Connection, a Schema and a
     Script group. Choose "Pick existing" for a group that is already in the
     registry, or "+ New group" and type a name.
  2. Type the migration under "SQL"
  3. Type the statements that undo it under "Rollback SQL". Deploy needs them
     to undo this version. To save without them, tick the box that starts
     "Save without a rollback".
  4. Optionally fill in the "Change log"
  5. Under "Version", check the number. It is suggested from your SQL and is
     always higher than the version applied to the database and the highest
     one in GitHub. "Version bump" lets you pick another step, and "Check
     GitHub again" reads the registry once more.
  6. Click the save button, which reads "Save", the version number, then
     "to GitHub"
  7. When it has saved, follow the link to the file on GitHub, or the link to
     the Deploy page to run it

Do not write COMMIT, ROLLBACK or other transaction statements in either box.
Deploy runs the whole script in one transaction of its own, and the page will
not save a script that has them.

If a version was saved without a rollback, "Add a missing rollback" at the
bottom of the page adds one to it later.

If AI assistance is on (section 11), "Write it with AI" drafts a script for
you: type what it should do under "What should the script do?" and press
"Write the script". Read the draft before you save it.

Saving needs "Save scripts to the registry". If the page says the GitHub
registry is not set up, an admin adds it on the Admin screen, under GitHub.

Once a version has been deployed, it is recorded in a ledger. The ledger is
stored in the target schema's `script_patch` table:
  • script_name: the family name (e.g., "users_migration")
  • version: semantic version (e.g., "v1.0.0")
  • title: short description of what changed
  • change_type: breaking (schema incompatible), additive (backward compat),
    patch (bug fix), or unknown
  • sql_content: the exact SQL that was applied (used for replay)

VERSION SYNC
------------
Go to Version Sync (left sidebar). This compares two schemas' ledgers.

  1. Pick a Source: a connection and a schema (ahead, has more versions
     applied)
  2. Pick a Target the same way (behind, missing some versions). The button
     between the two pickers swaps Source and Target.

There is no button to start it: as soon as both are picked, the page reads
both ledgers and shows:
  • "Missing on the Target": versions the Source has but the Target lacks, in
    the order the Source ran them (these can be replayed)
  • "Cannot be replayed forward": versions the Target is already at or above.
    A replay only moves forward, so the server refuses these.
  • "These schemas have diverged.": the Target has versions the Source does
    not, so a replayed script may clash with the Target's own changes
  • "You’re up-to-date!" when the Target has every version the Source has

REPLAYING VERSIONS
------------------
  1. The missing versions are listed in the order they will run
  2. Each row has a "Run" button. It replays the versions from the top of the
     list down to that row, because a later version may depend on an earlier
     one. A button above the list replays every version in the list, in one
     transaction.
  3. Pressing one opens the "Replay" dialog. Nothing has run yet. It shows
     "What runs, in order", the Target it runs on, and a tick box for each
     thing you must have read first: breaking migrations, statements that
     delete rows, and a drift check that did not pass.
  4. Click "Dry run" to rehearse it (the scripts run and are then rolled back,
     so nothing is written), or the "Replay" button to do it for real. On a
     production Target the Replay button says so, and both a replay and its
     dry run need an approval (see WHO MAY APPLY in section 10).
  5. Each version's stored SQL is executed against the Target in order
  6. A new ledger entry is added to the Target's script_patch table

Important: Replay assumes the stored SQL uses unqualified table names
(no schema prefix). The apply route sets `search_path` to scope them
to the target schema automatically.

If a version has no stored SQL (it was applied before the app stored it), it
is marked as one that can't be replayed.

A replay writes to the Target, so it needs the same permission as Deploy, "Apply
or revert migrations", and a Target whose connection lets your role run
migrations (see "Who may run migrations here" under Connections). Without the
permission the lists can still be read, but there is nothing to press, and the
screen says why.

7. VISUALIZER
================================================================================

Visualizer draws an interactive entity-relationship diagram (ERD) of any schema.

OPENING VISUALIZER
------------------
  1. Go to Visualizer (left sidebar > Visualizer)
  2. Pick a connection, then one of its schemas
  3. The diagram renders automatically

USING THE DIAGRAM
-----------------
  • Boxes represent tables; text inside shows columns
  • Lines show foreign key relationships
  • Click a table to highlight paths that reference it
  • Drag to pan, scroll to zoom
  • Double-click the divider (in side-by-side mode) to reset the pane sizes

SINGLE vs. SIDE-BY-SIDE
-----------------------
  • Single: view one schema at a time
  • Side-by-side: compare two schemas side by side (very useful for spotting
    structural differences visually before you compare)

The layout is responsive. On mobile/tablet, the visualizer forces single-pane
mode (dragging a divider is unwieldy on touch).

8. DRIFT DETECTION
================================================================================

Drift monitors unintended schema changes over time.

HOW IT WORKS
------------
When you first track a schema, a baseline snapshot is saved. Drift is calculated
by comparing the live database against that snapshot.

If the live schema no longer matches the snapshot:
  • Drift status changes to "drifted"
  • Details show which tables/columns changed, when it was first detected
  • The drift page offers four ways to deal with it (below)

WHY DRIFT MATTERS
-----------------
In a production environment, untracked schema changes are a warning sign:
  • Developers may have applied emergency hotfix migrations without versioning
  • Bugs in production schemas should be tracked and replayed to staging
  • Drift helps audit compliance: all schema changes should be intentional

VIEWING DRIFT DETAILS
---------------------
Go to Drift (left sidebar > Drift). Pick a schema.

You'll see three tabs:
  • Drift detail: the expected structure (the baseline) next to the actual
    one (the live database), and the recent checks for this schema
  • Audit log: every recorded drift check, newest first. You can filter it by
    status and search it by schema, connection or summary.
  • Schedule: how often each tracked schema is checked without anyone asking.
    Pick a time under "How often" (from "Manual only" up to "Once a day").
    The tab also shows when each schema was last checked, when its next
    check is due, and whether automatic checking is running on this server.

If AI assistance is switched on (section 11), the Drift detail tab also has a
panel "Explain this drift" with a button "Explain with AI".

RESOLVING DRIFT
---------------
Above the diff, a drifted schema offers four actions. Each one does exactly
what it says and nothing else:

  • Author a migration — opens Compare with this live schema loaded, so you can
    write the migration that makes the change intentional. No migration is
    invented for you.
  • Re-baseline to live — accepts the current structure as the new expected
    snapshot. Behind a confirm, because it is the one that makes the drift
    disappear without anybody having explained it.
  • Acknowledge — records the drift as reviewed. It changes nothing in the
    database; it only says a person has looked.
  • Check drift now — re-runs the check, in case the schema has moved since the
    page was drawn.

The four block one another while any of them is running: re-baselining replaces
the snapshot a check is comparing against, so running both at once would leave
the recorded answer down to which request came back first.

A schema that is back in sync keeps only the re-check.

9. PERFORMANCE
================================================================================

Performance answers three separate questions about a database you already have
a connection to: what is this schema likely to be slow at, why is this one
query slow, and what has this schema been doing over time.

Go to Performance (left sidebar > Performance). Pick a connection and a schema
at the top of the page. The picker sits ABOVE the tabs, so moving between tabs
keeps your choice — all six need the same connection and schema to start with,
and choosing a database again on every tab would be the wrong kind of careful.

THE SIX TABS
------------
  • Suggestions      what this schema is likely to be slow at
  • Analyse a query  what the server would actually do with one query
  • History          every query analysed here, and whether it has got slower
  • Live activity    what the server is doing at this moment
  • Trends           how this schema has changed over time
  • Alerts           what should count as a problem here

Three of them read the live database the moment you ask and store nothing about
the schema (Suggestions, Analyse, Live activity). Two can only show what was
collected earlier, so they say when they are empty rather than drawing a chart
of nothing (History, Trends). The last one writes rather than reads: Alerts is
the only tab that changes what the others will say.

SUGGESTIONS
-----------
Worked out from the schema's own structure, and from PostgreSQL's record of how
its tables have actually been read. Typical findings:

  • A foreign key with no index behind it
  • A table with many dead rows waiting to be cleaned up
  • An index that has not been used since the counters started, or one already
    covered by a wider index
  • A table the server almost always reads with a sequential scan
  • A table with no primary key, or a primary key on a text column
  • A table large enough that partitioning is worth considering
  • Column types that usually cause trouble later: timestamp without time zone,
    character(n), serial rather than an identity column

Each finding says what to do about it. The ones that are schema changes can be
taken away as SQL, from the box under the list:

  • Copy as one script / Download .sql — every ticked fix as one file, with a
    header saying which connection and schema it came from
  • Save as a migration — the ticked schema changes AND their rollback, handed
    to the Script Editor, where the normal version-and-save flow takes over

Query rewrites and judgement calls are not offered as SQL: a rewrite changes the
query rather than the database, and a judgement call needs you to choose first.
"Save as a migration" is left out for a role without "Save scripts to the
registry" (out of the box, Viewer), because saving goes through the Script
Editor and offering it would only lead to a refusal at the end. The box says so,
and Copy and Download still work. A fix that belongs to a DIFFERENT schema than
the one you picked is listed separately and can be copied or downloaded, but not
saved: a migration is written for one schema.

ANALYSE A QUERY
---------------
Paste one query and press Analyse. You get:

  • The server's own plan, step by step, in plain English
  • A score out of 100
  • Anything in the plan or in the SQL itself that usually costs more than it
    looks

Only queries that READ can be analysed: SELECT, WITH, VALUES or TABLE. One
statement at a time, and without a leading EXPLAIN — the screen adds that
itself. Anything that would write is refused, both before it runs and again
after the plan comes back.

By default nothing is executed: the plan is an estimate, and the screen says
"Estimated". Tick "Run it and measure" and the query really is run (inside a
transaction that is always rolled back) for real row counts and a real execution
time; the screen then says "Measured". That tick-box needs "Measure a query on a
live database" (out of the box, Editor and Admin). Without it the box can't be
ticked and says why, but analysing still works. A measured query is cut off
after 15 seconds so a bad one cannot sit on the server.

Every analysis is written to History automatically.

HISTORY
-------
Every query analysed against this schema, newest first, with what it scored and
what it cost, plus a day-by-day trend.

Pick one query and you get each of its runs set against an earlier one. That
comparison is the point of the tab: a single slow reading tells you a query is
slow, and only two readings tell you it has got slower.

LIVE ACTIVITY
-------------
One reading of what the server is doing right now: what is running, what has
been running too long, and what is sitting in an open transaction holding locks
nobody is using. The reading carries the moment it was taken, because a list of
long-running queries with no timestamp on it ages into a lie.

PostgreSQL reports activity for the whole server, not per schema, so this tab
shows every session on that server — not only the schema you picked above.

TRENDS
------
How this schema has changed over time: its structure, its size on disk, and how
often it drifted from its baseline.

These readings are not gathered when you open the tab. One is taken every time
a drift check runs, so a schema has a history exactly when the app has been
watching it. A schema nobody tracks says "not tracked" rather than showing an
empty chart — an empty chart says "nothing happened", and "not tracked" says
"nobody was looking". To start a history, track the schema (Dashboard > Track a
schema) and let its drift checks run.

ALERTS
------
What should count as a problem for this connection and schema. Five rules:

  • Query slower than …            ms
  • Query scores below …           / 100
  • Session running longer than …  s
  • Cache hit ratio below …        %
  • Dead rows above …              %

Every rule starts switched OFF, with a suggested number already in the box. The
suggestion is this app's guess, not a fact about your database, so nothing is
flagged until you turn a rule on and agree its number.

10. DEPLOY & APPLY
================================================================================

The Deploy page consolidates the migration flow: from authored SQL to applied
ledger entry.

WORKFLOW
--------
Deploy does not take pasted SQL. It runs versions that were saved to the
GitHub registry, from Compare & Author (section 5) or the Script Editor
(section 6). The page has three steps, shown along the top: Pre-flight, Run
and Verify.

  1. Save the migration to the registry first (section 5 or 6)
  2. Go to Deploy (left sidebar > Deploy, or the link shown after a save)
  3. On Pre-flight, pick:
     • Connection (which database)
     • Schema (which schema in that database)
     • Script group (the family of versions to bring this schema up to)
  4. Click "Check database". The page reads the target's ledger and shows:
     • "Applied to target": the version this schema is on now
     • "Version timeline": every version of the group, and which are applied
     • "Pending migrations": the versions the target does not have yet
  5. Choose how far to go. Each pending row has a "Run" button for the
     versions up to that row, and "Run all" picks every pending version.
     These buttons only choose the range. Nothing runs yet.
  6. Read the "Pre-flight checklist". It covers, among other things, that the
     target can be reached, that you may run on it, its environment, the
     applications it is used by, that no script holds a transaction statement,
     the approval, the ledger table and the drift check.
  7. Tick the boxes the page asks for. There is one for a production target,
     one for breaking migrations, one for statements that delete rows, and
     one when the drift check did not pass.
  8. Click the "Dry run" button to rehearse: the scripts run against the
     target and are then rolled back, so nothing is written. On a
     production target a dry run needs the approval as well, and the same
     approval then covers the real deploy. A dry run stops any statement
     that takes longer than five minutes.
  9. Click the "Deploy" button to run for real. Both buttons name the range of
     versions, and Deploy adds "to production" on a production target. After
     a clean rehearsal the Run step offers "Deploy for real".
 10. The Run step shows how each migration went. If the run stopped, nothing
     was applied; you can go "Back to Pre-flight" or press "Run again".
 11. The Verify step shows "What was applied" and a "Verify diff", with links
     to Version Sync and Drift and a "Re-check target" button.

If AI assistance is switched on (section 11), Pre-flight also has a panel
"Review this run" with a button "Review with AI".

ROLLING BACK
------------
On Pre-flight, "Plan a rollback" opens the rollback plan for the script
group. Choose the version to roll back to. The page shows the order the
steps run in and the rollback SQL of each one. "Dry run the rollback" rehearses
it without changing anything, and the roll back button next to it does it for
real. A rollback needs the same permission, and on production the same
approval, as a deploy, and so does its dry run (see WHO MAY APPLY below).

Below that, "Rollback history" and "Deploy history (all attempts)" list what
was run on this schema for the group.

EXECUTION
---------
When you click the Deploy button:
  • The script_patch ledger table is created if the schema does not have one
  • A transaction begins
  • An advisory lock is acquired (prevents concurrent applies of the same
    script name + version)
  • Your SQL is executed (unqualified table names are scoped to the target
    via `SET LOCAL search_path`)
  • The script_patch table is updated with the new ledger entry
  • The transaction commits

If any step fails, everything rolls back. You'll see the error message.

One exception: a new enum value (ALTER TYPE ... ADD VALUE) is added before the
transaction opens, because PostgreSQL does not let a new value be used in the
transaction that adds it. It stays even if the rest of the run fails. The page
warns about this before the run.

WHO MAY APPLY
-------------
Applying, reverting and replaying all write to a database, so all three need
"Apply or revert migrations" (out of the box, Editor and Admin). The Target
connection has the last word on top of that: it can allow anyone who may run
deployments, admins only, or nobody (see "Who may run migrations here" under
Connections). When either one stops you, Deploy says which, next to the buttons
it switches off.

A Target labelled production needs one more thing: an approval for that exact
run, from a second person. Asking for one needs "Request a production approval"
(out of the box, Editor and Admin), and giving one needs "Approve production
runs" (out of the box, Admin only, but an admin can give it to another role).
Nobody can approve their own request. An approval covers one run of the SQL it
was given, for up to 7 days: change the SQL, or wait longer, and it needs
approving again.

A dry run on production needs the approval too. A rehearsal still runs the
script on the production database: it holds locks while it runs, and
sequence numbers it uses are not given back when it is rolled back. A dry
run does not use the approval up, so one approval covers the rehearsal and
the real run after it.

Two exceptions let you approve your own request, and the approval is then
recorded as a self-approval:
  • While sign-in is switched off for testing there is only one person.
  • An admin has switched the organization's two-person rule off on the
    Organization tab (section 11). You still need "Approve production runs".

BEST PRACTICES
--------------
  • Always test migrations on a dev/staging schema first
  • Use semantic versioning (v1.0.0, v1.0.1, v1.1.0, v2.0.0)
  • Write clear script names and titles (future you will thank you)
  • Pick the right change level when you save (breaking, additive or patch), so
    Deploy and Version Sync can warn before a breaking change runs
  • Store migrations in version control (Git); don't rely on the app as your
    single source of truth

11. PEOPLE AND THE ORGANIZATION (ADMIN)
================================================================================

The Admin page, titled "People and the organization", has up to five tabs:
  • Users: who is in this organization, and which role each person has
  • Roles & permissions: what each role may do
  • Organization: its name, its two-person rule, and deleting it
  • GitHub: the repository where the organization's scripts are kept
  • AI: whether the organization uses AI assistance, and for what

ACCESSING ADMIN
---------------
Go to Admin (left sidebar > Admin). Each tab shows only to a role allowed to
see it, and Admin shows in the sidebar to anyone who may see at least one of
the five. On a new install that is the Admin role alone.

The Roles & permissions, Organization and AI tabs are for Admin only: no other
role can be given them, so no role can make itself an admin. The Users and
GitHub tabs can be given to another role, so an admin can make, for example,
a role that looks after people and nothing else. If you don't see Admin in
the sidebar, ask an admin.

THE USERS TAB
-------------
The Users tab lists everyone in this organization. For each person you may
manage, there is:
  • A role picker. It offers only the roles you may hand out (see THE RANK
    RULE below).
  • Remove access (the bin button), which asks you to confirm first.

A change of role applies straight away: the screen shows it at once and puts
it back if the server turns it down. One change runs at a time, and each one
is listed under Recent changes on the Roles & permissions tab.

Removing someone takes away their access to this organization at once. Their
sign-in account (their Microsoft account, for example) is not touched, but
signing in no longer brings them here. They are back only if someone invites
them again or they use a join link that is still open, so cancel any link you
don't want them to have (see INVITING PEOPLE). If this was their only
organization, their profile in the app is deleted too. The desktop app has no
invitations: someone removed there comes back as a Viewer if they sign in to
it again.

While sign-in is switched off for testing, nobody new is added to this list:
everyone using the app is the same stand-in admin. The tab says so, and
points you to View as (below) for seeing the app as another role.

INVITING PEOPLE
---------------
Under the list is "Invite people", for a role that may invite. There are two
ways in:
  • To an email address: pick the role they will get. Only someone who signs
    in with that address can take it, once, within 7 days.
  • As a link: anyone who opens it and signs in joins as a Viewer. Pick how
    long it stays open: 1, 7 or 30 days (7 to begin with).
The app sends no email itself. When you make an invitation, its link is shown
once, with "Copy link": copy it then and send it yourself. Invitations nobody
has taken yet are listed under "Waiting to be taken", each with "Cancel
invitation". Each one made, canceled or taken is listed under Recent
changes. The desktop app has no invitations.

THE RANK RULE
-------------
Nobody can give someone a role, change their role or remove them when that
role can do something their own role can't. A role that can do exactly as
much as theirs is fine. So a role that may manage people still can't make
anyone an admin, or touch an admin: only Admin can give or take away the
Admin role. A person whose role is out of your reach has no controls on their
row, and the server turns such a change down by itself, for example "You
can't give someone the Admin role. It can do things your role (People Lead)
can't."

SELF-LOCKOUT PROTECTION
-----------------------
Your own row has no controls at all: it reads "Your account" where everyone
else has a role picker and a remove button. You can't change your own role or
remove yourself from this screen, whether or not other admins exist.

The server enforces two more rules, so nothing gets round them by another
route:
  • The last admin can't be given another role: "This is the last admin.
    Promote someone else first."
  • The last admin can't be removed, and neither can your own account.

To step down as an admin, make somebody else an admin first and ask them to
change your role.

THE ROLES & PERMISSIONS TAB
---------------------------
Only the Admin role sees this tab. At the top are the steps for setting up a
role:
  1. Pick a role, or make a new one.
  2. Turn on what it may do, then press "Save changes".
  3. Give it to people on the Users tab.
While sign-in is switched off for testing there is a fourth: check it with
View as on the sidebar.

Every role has a card with its name, a few words on what it adds up to, and
how many people have it. The words are worked out from what the role may do,
unsaved changes included:
  • Everything, always (Admin)
  • Can run migrations
  • Can change things
  • Read-only, plus drift checks
  • Read-only
  • Nothing turned on
"One role" shows one role at a time, and "Compare roles" shows them all side
by side.

ONE ROLE AT A TIME
------------------
Pick a role's card to open it. At the top are its name, its description and
how many people have it, with "See them on the Users tab" to go there.

At a glance answers the four things people ask about a role first:
  • Changes things: can it change anything at all, rather than only look?
  • Runs migrations: a yes reads "Yes, where the connection allows", because
    each connection can still say no in its own setting (section 3)
  • Approves production: can it approve production runs?
  • Manages people: can it invite people, change their role or remove them?

Under that is what the role may do, as plain sentences with a tick box each,
grouped under the same screen names as the sidebar, in the sidebar's order.
Each feature's see or open line comes first, and the lines that need it are
indented under it. Three kinds of line carry a tag, because they need more
care:
  • Writes to a database (red): Apply or revert migrations
  • Production (red): Approve production runs
  • Live database (amber): Cancel a stuck query on a live database, and
    Measure a query on a live database
A few lines have a short note under them as well (see LINES THAT NEED A WORD
MORE below).

Turning a line on also turns on its feature's see or open line, because none
of the others can be reached without it. Turning a see or open line off also
turns off the lines under it. Either way the tab says what else it changed,
under that feature, with an Undo button that puts everything back as it was
before the click.

On every role but Admin, the Roles & permissions and Organization tabs are
left out, and a locked line under Admin says why: they are for Admin only.
Admin itself shows every line turned on, and none of them can be changed, so
that nobody can lock every admin out of this page.

A line you have changed but not saved is marked "Unsaved", and so is the
role's card. The bar at the bottom says in words what saving will do, for
example "Viewer will be able to add a connection." Press "Save changes",
or "Discard" to drop the changes. Unsaved changes are kept for each role
while you move between roles.

A save applies straight away, on the server. Anyone with that role who has the
app open sees the new buttons once they reload the page. If two admins save
the same role, the later save is the one that stands.

COMPARE ROLES
-------------
"Compare roles" shows every role side by side: the four At a glance answers
first, then every line, grouped by screen, with Yes or No for each role. It
only shows; to change a role, pick its card. It shows what is saved, so
unsaved changes count once they are saved, and it says so while there are
any.

LINES THAT NEED A WORD MORE

ADDING A ROLE
-------------
  1. Press "New role"
  2. Name: up to 40 characters, with at least one letter from A to Z or a

Then change what it can do if needed, and give it to people on the Users tab.

RESETTING AND DELETING A ROLE
-----------------------------
  • "Reset to default" puts Viewer or Editor back to the lines it starts with

    at its defaults.
  • "Delete role" removes a role an admin made. It is switched off while anyone
    still has the role: give them another role on the Users tab first. The

RECENT CHANGES
--------------
At the bottom of the tab is a list of changes, newest first, with who made
each one and when. A save names the lines it turned on and off. Roles made,
deleted or given to people, invitations, people removed and changes to the

VIEW AS (TESTING)
-----------------
While sign-in is switched off for testing, everyone is the same stand-in admin,
so nobody can sign in as a viewer to check what a viewer sees. View as is that
check. It sits under your name in the sidebar while the sidebar is expanded.
  1. Pick a role. The page reloads, and from then on every screen, and the
     server too, treats you as that role.
  2. Pick "Admin (everything)" to go back.
The choice lasts for this browser session. With real sign-in View as is not
there, and the server ignores it.

THE ORGANIZATION TAB
--------------------
Only the Admin role sees this tab. It has three parts:
  • Name: rename the organization. Its address (the part after the site name)
    stays the same, so saved links keep working.
  • Two-person rule: on for every new organization. While it is on, a
    production deploy or rollback waits for someone other than the person who
    asked. Switching it off asks you to confirm first; people can then approve
    their own requests, and each one is recorded as a self-approval. Both
    switches are listed under Recent changes.
  • Delete this organization: type its name to confirm. It deletes the
    organization's connections, scripts, approvals, invitations and change
    log, and takes everyone out of it. Their accounts stay, and so do scripts
    already in the GitHub registry. The first organization on an install
    cannot be deleted, and nothing can be deleted on the desktop app or while
    sign-in is switched off for testing.

THE GITHUB TAB
--------------
This tab decides which GitHub repository the organization's scripts are kept
in. On a new install only Admin sees it, but an admin can give another role
"See which GitHub repository the organization uses", and "Change the GitHub
repository or its access token", without making it an admin.

"Where scripts are kept" says what is set now: the repository (and its folder,
if it has one) and who saved it, or that the organization uses the GitHub
settings the app was set up with, or that it is not connected yet.

To connect a repository, or change it:
  1. Repository: owner/name, or paste its address
  2. Access token: a GitHub token that may read and write that repository. It
     is stored encrypted and never shown again. To keep the saved one, leave
     this blank.
  3. Press "Save". The app checks the repository and the token with GitHub
     before it saves them.
"Remove" takes the settings away, after you confirm. The scripts already in
the repository stay there. Saving and removing are both listed under Recent
changes.

Making an access token, on GitHub:
  1. Open Settings, then Developer settings, then Personal access tokens, then
     Fine-grained tokens, and choose Generate new token.
  2. Under Repository access, choose Only select repositories, and pick the
     repository.
  3. Under Permissions, set Contents to Read and write. The app needs nothing
     else.
  4. Generate the token, copy it, and paste it here.
A token stops working on the date picked when it was made: make a new one
then and paste it here. If the repository belongs to a GitHub organization,
that organization may have to approve the token first.

If the tab says the saved token can't be read, the server's encryption key has
changed since it was saved: paste the token again. The desktop app keeps its
GitHub settings in its own Settings window instead (File > Settings).

THE AI TAB
----------
Only the Admin role sees this tab. AI assistance is off until an admin
switches it on here, and it needs an AI service: either one set up on the
server, or the organization's own key (below). With neither, the tab says
"No AI service is set up on this server".

  • The switch "Let people in this organization use AI assistance" turns it
    on or off for the whole organization. Turning it on asks you to confirm
    first ("Switch AI assistance on?", then "Switch on").
  • What is sent to the AI service: table, column, index, constraint and view
    definitions, and the SQL of the scripts being reviewed. Never rows of
    data, passwords, connection addresses or anyone's details. While the
    switch is off, nothing about the organization's schemas is sent.
  • "Organization AI key": save one key for the whole organization, used in
    place of the server's AI settings. Pick the Service (Anthropic Claude,
    Google Gemini or OpenAI) and paste the API key. You can also name the
    model for reviews and explanations and the model for short summaries.
    After "Save key" the tab shows only which service the key is for and its
    last four characters. "Remove key" puts the organization back on the
    server's settings.
  • "Features": one switch for each AI feature, so you can keep some off:
    Compare change summary, Migration review before deploy, Explain drift,
    One line in drift alerts, Write SQL from plain words, and Schema chat.
  • A usage card for the last 30 days: how many calls were made, how many
    gave no usable answer, the tokens used, and how long answers took.

Using AI needs the line "Use AI assistance" (out of the box, Editor and
Admin). Where it is on, you meet it in these places: "Summarize with AI" on
Compare, "Review with AI" on Deploy, "Explain with AI" on Drift, "Write it
with AI" in the Script Editor, and "Ask AI" in the top bar, which opens the
schema chat. The app checks every answer against its own engine before
showing it, and nothing the AI writes runs without someone approving it.

THE REQUESTS PAGE
-----------------
Requests is a page of its own (left sidebar > Requests), and every member of
the organization can open it. It is where you ask for something your role
can't do yet, and where the people who can answer see what is waiting.

Asking (every role except Admin, which already has everything):
  1. Under "What do you need?", choose the thing your role can't do yet, or
     "Something else"
  2. Say why if you like ("Why? (optional)"), then click "Send request"
  3. The request shows under "Your requests", with its answer once it has
     one. "Withdraw" takes it back.

Answering: people who may change what a role can do, or change someone's
role, see "Waiting for you". For each request they can allow the thing for
everyone in the asker's role, give the asker another role, mark it as done,
or decline.

Production runs show here too. A run that needs your approval reads "Needs
approval" with a link "Review it on Deploy". A run of yours that has been
approved reads "Ready to run" with a link "Open it on Deploy".

13. TROUBLESHOOTING
================================================================================

"Unable to compare" or Connection Error
----------------------------------------
  • Verify the saved connection credentials are correct (Connections page)
  • Check network connectivity (schema introspection queries the live DB)
  • If using SSL, ensure the certificate is valid
  • On Neon, make sure you're using the pooler endpoint, not the direct one
  • Click "Test" on the connection's row (or "Test now" while editing it) to
    get a detailed error

"Version already applied" or Duplicate Version Error
-----------------------------------------------------
  • You tried to apply the same (script_name, version) to a schema twice
  • Check the script_patch table: `SELECT * FROM schema_name.script_patch`
  • Save the change as a new, higher version. Deploy only moves forward: a
    version must be above every version already applied for that script. A
    run that failed wrote nothing to the ledger, so it can simply be run
    again.

"Drift detected" but I didn't change anything
----------------------------------------------
  • Drift might be from an earlier change you forgot about
  • Check the Audit log tab on the Drift page to see when it was detected
  • If the live structure is the one you want, use "Re-baseline to live" on the
    Drift page to accept it as the new expected snapshot. (The Refresh button
    on the Dashboard only re-reads the list; it does not touch a baseline.)
  • If it's spurious (a bug), let your admin know

"Pre-flight check failed" or "SQL syntax error"
------------------------------------------------
  • Check your SQL for typos (missing semicolons, mismatched quotes)
  • Make sure unqualified table names are correct (search_path will scope them)
  • If you reference a schema explicitly (schema.table), it may not scope correctly
  • Try running the SQL manually in a SQL IDE first to confirm it works

"Can't see schemas in the Visualizer / Compare dropdown"
---------------------------------------------------------
  • Make sure you've selected a connection (not all connections have all schemas)
  • Check that the schema exists: `\dn` in psql or look in the Connections page
  • Introspection queries may time out on very large databases
  • Refresh the page and try again

"I signed in but the sidebar shows no role"
--------------------------------------------
  • No role pill means the app has no session for you at all — you are not
    signed in, even if a screen is visible. Sign in from /login.
  • If it says "auth off" instead, authentication is switched off on this
    server and everybody is being let in as an admin, or as the role picked in
    View as. See SETTINGS in section 12.

"I'm locked out of the app (no 'admin' role and need to make changes)"
---------------------------------------------------------------------
  • Ask an existing admin to grant you the admin role (Admin page)
  • If no other admin exists, contact your system administrator to unlock you

A button is missing, or "Your role (...) can't ..."
---------------------------------------------------
  • Your role doesn't have the permission that button needs. The message
    names it by its line on Admin > Roles & permissions, for example "Add a
    connection" (under Connections). Section 11 lists every line.
  • Ask an admin to turn that line on for your role, then reload the page.
  • If you are using View as, pick "Admin (everything)" to go back.
  • A message that starts "Could not check" is different: the app's own
    database did not answer, so no permission is missing. Try again in a
    moment.

"Script Patch table doesn't exist"
-----------------------------------
  • When you apply a migration for the first time, the app auto-creates
    the script_patch table in the target schema
  • If creation fails, check your permissions (you may need ALTER SCHEMA rights)
  • Manually create the table if needed (see apply route source code for DDL)

================================================================================
GLOSSARY
================================================================================

Schema: A namespace in PostgreSQL. e.g., `public`, `auth`, `inventory`.
        All tables belong to a schema.

Connection: A saved PostgreSQL database (host, port, user, password).
           You can have multiple connections and compare across them.

Drift: Unintended divergence of a live schema from a baseline snapshot.

Ledger: The script_patch table that tracks all applied migrations per schema.

Version: A semantic version (v1.0.0, v1.0.1, etc.) that uniquely identifies
         a migration in the script_patch ledger.

Script Name: A family name for related migrations (e.g., "users_migration").
            Same script_name can have multiple versions (v1.0.0, v2.0.0).

Foreign Key (FK): A constraint that links a column in one table to a primary
                  key in another, enforcing referential integrity.

Migration: A versioned SQL script that changes a schema (add/drop/alter tables,
          columns, constraints, etc.).

Replay: Re-running a stored migration (from the script_patch ledger) against a
       different schema to synchronize it.
