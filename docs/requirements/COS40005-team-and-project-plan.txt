PART 2 Project overview and plan


    1. PROBLEM STATEMENT

In modern software development, database schemas frequently change as systems continue to
evolve and new features are added. However, managing these changes across different
environments such as development, staging, and production is often done manually. This manual
process can lead to various issues, including inconsistencies between environments, version
conflicts, missing updates, and deployment errors. As a result, teams may struggle to maintain
accurate, synchronized, and up-to-date databases, which can affect system performance and
reliability.

Furthermore, without proper version control and tracking, it becomes difficult to monitor what
changes have been made, who made them, and when they were applied. This increases the risk of
errors and makes it harder to fix problems when they occur. Therefore, this project aims to
develop a database schema comparison and version control system that can automatically detect
differences between schemas, manage schema versions efficiently, and generate SQL migration
scripts for controlled updates. The main objective is to improve efficiency, reduce human errors,
enhance collaboration among team members, and provide a more reliable and structured way of
handling database changes across different environments.


    2. SCOPE

The scope of this project is to develop a system that can compare database schemas by finding
differences in tables, columns, indexes, and relationships. The system will also track schema
versions, generate SQL scripts (including rollback scripts), and provide simple query analysis and
performance suggestions. It will include role-based access control to manage user permissions
and integrate with Git to store approved scripts and track changes.

However, this project will not include designing a database from the beginning. It will mainly
focus on PostgreSQL and may not support all types of databases. It also will not automatically
deploy changes to production without user approval, as users must review changes first. Features
not related to database management are also not included in this project.

    4. HIGH-LEVEL REQUIREMENTS

This project is a new prototype system designed as a standalone tool that connects with external
components such as PostgreSQL databases, GitHub for version control, and Microsoft
authentication services. The system will provide main functional features like schema
comparison, version tracking, SQL migration and rollback script generation, and basic query
performance analysis to help users manage database changes more efficiently.

For non-functional requirements, the system must ensure security through proper authentication
and access control. It should also have good performance and fast response time, be easy to use
with a clear interface, and be reliable when handling schema comparisons and updates.

From a technical side, the system will be developed using Next.js as the main framework,
PostgreSQL with Sequelize for database management, and Tailwind CSS for styling the interface.
Docker will be used for deployment to ensure consistency across environments, and Jest will be
used for testing to maintain system quality and reduce errors.

Our proposed solution is a web-based system for comparing database schemas across
environments, tracking schema versions, and managing migration scripts in a safer and more
organized way. The main issue behind the project is that database changes made in development
are not always recorded properly before moving to stage or production. Because of that, teams
can end up with missing columns, wrong column types, missing tables, or other schema
mismatches that only show up later when the live system is already being used. Based on the
project description and the client discussion, we see the project as mainly centered around two
core areas, which are schema comparison and migration version control.

At a high level, we are planning to use layered architecture because it is easier for us to design,
build, and explain. The system will have a frontend layer, an application layer, and a data layer.
The front end will be responsible for the user interface, the application layer will handle the main
processing and decision making, and the data layer will handle both the system’s own stored
records and the external databases being checked. We think this is the most practical approach for
a student team because it keeps things structured without making the design too complicated too
early.




For the frontend, we plan to use Next.js. This choice is mainly because it was the framework
requested in the client’s stack guidance, but also because it gives us a clean way to build the user
interface together with server-side logic in one project structure. The frontend will act as the main
point of interaction for users and will support the overall flow of authentication, connection
management, schema comparison, migration review, and version tracking. Since the intended
users are mainly IT staff, including some who are not deeply confident with database details, the
interface needs to make the process clearer and more manageable than doing everything
manually.

The main application logic will sit behind that frontend layer. This part of the system will handle
authentication, validation, schema comparison processing, version checks, migration SQL
generation, and GitHub integration. Instead of directly making uncontrolled changes to a target
database, the application logic will focus on detecting differences, preparing the required SQL,
and supporting a review-based workflow. That is an important design choice for us because the
client’s main concern is not just comparison itself, but making schema changes more visible,
traceable, and controlled before anything is applied.

For the system’s own stored data, we plan to use PostgreSQL together with Sequelize ORM. This
part will likely be used for users, saved database connections, comparison history, approval
records, migration history, and related application data. For the actual schema inspection work,
though, we expect to rely on raw SQL queries against PostgreSQL metadata rather than ORM
alone. The reason is simple. Schema comparison is too specific and too tied to database internals
to depend fully on ORM abstraction. We will likely need to query system metadata directly to
inspect tables, columns, constraints, indexes, and version related information properly.

Authentication is planned through Microsoft account login using NextAuth, which follows the
stack direction given by the client. This makes sense for the kind of user expected to use the
system and keeps the design closer to something that could be adopted more seriously later if
needed. Docker is planned for containerised setup and deployment, mainly to keep development
and demonstration environments more consistent. Jest will be used later for testing, especially for
main pages and user facing functionality.

In terms of overall flow, architecture is meant to support a process where a user can work from
authenticated access into connection management, then into schema comparison, and finally into
migration handling and version tracking. The important point here is not the exact screen by
screen behavior yet, but the fact that the system is being designed around workflow. The
application should help users inspect differences between environments, understand what is out of
sync, and move toward a safer migration process instead of relying on memory or manual
tracking.

We also looked at a few alternative approaches before settling in this direction. One option was to
use a more familiar stack such as plain React for the frontend with a separate backend using
Express or Flask. That would probably have been more comfortable for us at the start, especially
since some parts of the required stack are still new to us. Still, we decided not to go in that
direction because the application support guidance specifically points toward Next.js,
PostgreSQL, Sequelize, NextAuth, Docker, and Jest. Also, even though the client said the project
is not strictly intended for production right now, they also mentioned that a strong enough result
could still be considered for future use. Because of that, it makes more sense for us to stay close
to the requested stack rather than choosing something easier but less aligned.

Another approach we considered was trying to build the full feature set from the beginning,
including advanced reporting, query execution analysis, performance suggestions, monitoring

because it would be too much too early. Even the core comparison and version control parts

    7. QUALITY PLAN


Our quality goal is not just to make the system work once on our laptops. We want the
deliverables to be correct, understandable, reasonably safe, and usable for the kind of technical
users the client described. Since the project deals with database schemas and migration scripts,
quality matters a lot because even a small mistake can lead to wrong changes being suggested or
applied.


Quality expectations

First, the system should be functioning for the core workflow. If a user compares two schemas,
the system should correctly identify missing tables, missing columns, and column type
mismatches in the cases we support. We do not want the tool to give a false impression that two
schemas match when they do not. For the early prototype (by wk6), our target is that the main
comparison flow works on our planned test cases and samples.


Second, the system should be safe and user controlled. Generated migration SQL should not be
executed automatically. Users should be able to review and edit the generated scripts before
accepting them. This is important because automatic schema changes are risky, and the client
                                                                           UNIT CODE COS40005
                                                                             PORTFOLIO TASK 1
PAGE
                                                 16
clearly wanted a safer review-based flow. So, one of our quality expectations is that no
destructive action happens without an explicit user step.


Third, the system should be understandable to the target users. Even though the users are
technical, not all of them are expected to be strong in databases. Because of that, the interface
should clearly show what is missing from each schema, what the version gap is, and what script is
being proposed. Our quality expectation here is that key comparison results are shown clearly
enough that a user can understand the output without reading raw metadata only.


Fourth, the system should be traceable and auditable. Accepted migration scripts should have a
version, and their execution history should be recorded. This matters because one big problem in
the current situation is that changes are forgotten or not tracked properly. So, our quality target is
that approved changes leave a clear record, at least within the scope of our implemented features.


Fifth, the system should have basic reliability and validation. The app should validate connection
input, handle invalid ports or unreachable hosts, and fail safely instead of crashing. It should
handle cases where a version table does not exist and go back to structural comparison, as
mentioned earlier.

2. All main pages should be loaded without blocking errors during demo use.
3. Connection form validation should reject obviously invalid input before submission.
4. Generated migration SQL must always require manual review before acceptance.
5. Accepted scripts should include a recorded version number and timestamp.
6. Main prototype pages should have at least basic tests before the code review stage, in line with
  the compliance guidance.

Steps to assure quality

To reach those quality goals, we plan to do quality assurance throughout the project, not only at
the end.


We will start with requirement validation. Since this project is very client driven, we need to keep
checking that our interpretation of the core functions still matches what the client wants. We
already learned from the meeting that schema comparison and version control are the main
beginning modules, while query analysis and performance features are more secondary for now.
So regular requirement checking is part of quality for us, not just coding.


We will also use step-by-step development. Instead of trying to build the whole system at once,
we will develop the project feature by feature. For example, first schema comparison, then SQL
generation, then version tracking, then GitHub integration. This reduces the chance of building
too much on top of a weak base.


For testing, we plan several levels of checking. We will do manual testing on each feature while
building, especially for user flows such as sign in, adding connections, choosing schemas,
running comparisons, reviewing generated SQL, and viewing versions. We will also prepare
sample PostgreSQL schemas with controlled differences so we can test whether the system
detects the correct mismatches. For example, one test database may have an extra column,
another may have a different data type, and another may be missing a table. This gives us
repeatable test data for comparison logic.


We also plan basic integration testing of the full workflow. That means checking whether the
frontend, backend logic, application database, and external target database connections work
properly together. This is especially important because our project uses several linked tools and
not just one standalone page.

Specialized Research Topics

Schema Comparison Algorithms:

Information about the tables structures, columns, indexes and constraints was retrieved through
research into Pg System catalogs (pg_class, pg_attribute, pg_index, pg_constraint). In the end, a
two‑phase engine was implemented: first version detection (when there's a version table in place),
second structural comparison.



SQL Script Generation and Versioning:
Best practices of Liquibase and Flyway were discovered for creating both a migration (up) script
and rollback (down) script. Semantic versioning (x.y.z) based on breaking (major), additive
(minor), or minor fixes (patch). Scripts are organized in a version-controlled Git repository
located at the /scripts_init and /scripts_patch folders.


Query Analysis and Performance Monitoring:
In addition to examining PostgreSQL’s performance views (pg_stat_statements, pg_stat_activity,
pg_statio_*) and EXPLAIN plan parsing for sequential scans, missing indexes, and expensive
operations. We explored integrating AI (e.g. OpenAI API) to convert EXPLAIN output into
plain‑language recommendations. Performance metrics will be sampled at intervals, to avoid the
overhead of capturing many [key: value] pairs every second/minute/period. These performance
snapshots would then be stored on their own table.


Security and Access Control:
Research on securing database connection strings led to the use of environment variables and
Docker secrets. Role‑based access control (RBAC) is handled in NextAuth callbacks that map
Microsoft Entra ID groups to application roles (e.g., “Schema Admin”, “Read‑Only User”).
