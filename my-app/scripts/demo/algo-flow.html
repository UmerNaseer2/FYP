Stage 1 — Preprocessing
Build Incoming FK Maps (one per schema)
Before any comparison starts, the algorithm walks every table in each schema and builds a reverse index: "which tables point at me?" This is computed once and reused for every pairwise table comparison — so the FK graph lookup is O(1) per table, not O(n²).

Example from ecom_v1:
users ← referenced by orders.user_id
categories ← referenced by products.category_id
orders ← referenced by order_items.order_id
products ← referenced by order_items.product_id
Stage 2 — Pass 1: Exact Name Matching
Match tables that share the same name
Normalise every table name (trim whitespace, case-sensitive) and look each left table up in a right-side name map. Matches go straight to full scoring. No similarity threshold needed — a name match is a match.
✅ Exact matches found
categories ↔ categories
products ↔ products
orders ↔ orders
→ All go to full scoring
⏭ Unmatched — sent to Pass 2
Left only: users, order_items
Right only: customers, purchase_lines, payments
Stage 3 — Pass 2: Similarity Matching
Score every unmatched left–right pair, find mutual best matches
Score all combinations of unmatched tables (2 left × 3 right = 6 pairs here). For each left table, find its highest-scoring right candidate. For each right table, find its highest-scoring left candidate. A match is only accepted if both sides agree — i.e. each is the other's best option. This prevents one popular right-side table from absorbing multiple weak left-side matches.

Stage 4 — Table Pair Scoring (0–100)
Four weighted dimensions → normalised to 0–100
Run for every matched pair — both exact-name matches and similarity matches. Each dimension earns raw points; the total is scaled to 0–100 so the threshold constants stay meaningful regardless of how many dimensions contributed. The relationships dimension is skipped for tables with no FK involvement, and the remaining three dimensions fill the full 0–100 range instead.
① Name Similarity × 20
Levenshtein edit distance between the two table names, normalised by the longer name. 1.0 = identical, 0.0 = nothing in common.
sim = 1 − levenshtein(a, b) / max(len_a, len_b) pts = sim × 20 "users" vs "customers" → 1 − 4/9 = 0.56 → 11.1 pts "categories" vs "categories" → 1.0 → 20 pts
② Column Structure × 55
Each left column finds its best-scoring right column, and vice versa. All scores are averaged together (left pool + right pool). See Stage 5 for how individual column pairs are scored.
leftScores = [best score per left column] rightScores = [best score per right column] ratio = average(leftScores + rightScores) pts = ratio × 55 users vs customers → ratio 0.92 → 50.6 pts
③ Constraint Families × 15
Five families scored independently using signature-based Jaccard similarity, then averaged. See Stage 6 for signature details.
families = [PK, UNIQUE, FK, CHECK, EXCLUDE] each → Jaccard(left_signatures, right_signatures) pts = average(families) × 15 order_items vs purchase_lines: FK = 0.0 (schema names differ in signature) others = 1.0 → average 0.8 → 12 pts
④ FK Graph (Relationships) × 10
Compares which tables this table points to (outgoing) and which tables point at it (incoming), using multiset similarity on names and shapes. This is the strongest rename signal when names drift.
outgoing: multiset_sim(ref_table_names, shapes) incoming: multiset_sim(referring_table_names, shapes) pts = average(present buckets) × 10 users vs customers: incoming: ["orders"] vs ["orders"] → 1.0 → 10 pts
Final score formula:   score = (name_pts + col_pts + con_pts + rel_pts) × 100 / max_possible  →  rounded to 1 decimal place. When relationships is skipped (isolated table), max_possible = 90 instead of 100.
Stage 5 — Column-Level Detail
Two-pass column matching inside each matched table pair
Same two-pass logic as the table level, applied per column. Pass 1 matches by exact name. Leftovers go to similarity scoring.
Pass 1 — Exact column name match
Normalise names, look up in a map. Matched columns go straight to diff reporting. In orders: id, status, total_amount, placed_at all match exactly.
Pass 2 — Similarity on leftovers
Unmatched columns scored pairwise. In orders: user_id (left) vs customer_id (right) → score 51/60 → accepted column rename.

Column thresholds: ≥ 50/60 → accepted match  |  40–49/60 → possible rename  |  < 40 → no match (column only in A or B).
Type is the heaviest signal because type changes are usually breaking. Order is the lightest because column reordering is cosmetic.
Stage 6 — Constraint Diff
Five constraint families — signature-based matching
For each matched table pair, constraints are diffed across five families. Each family builds a signature per constraint — a string representing what the rule does, not what it's called — so renamed constraints still match. Strategy: match by name first, fall back to matching by signature.
PRIMARY KEY
Signature: ordered column list
"id" or "user_id|account_id"
UNIQUE
Signature: sorted column set
Jaccard on all unique constraint sigs
FOREIGN KEY
Signature: local cols → schema → table → ref cols → ON UPDATE → ON DELETE
All 6 parts must match
CHECK
Signature: normalised expression text
"check (price > 0)"
EXCLUDE
Signature: normalised expression text
Rare — most schemas score 1.0 here
Each constraint reports one of three outcomes: only in A (removed), only in B (added), or changed definition (same name, different rule). These feed directly into the compare report UI.
Output — CompareReport
Structured report returned to the UI
Everything the compare page renders comes from this single object.
matchedTables
All confirmed matches (exact + accepted renames) with full column diffs, constraint diffs, score breakdowns, and change lists.
tablesOnlyInA / tablesOnlyInB
Tables with no match on the other side and no rename candidate above the possible threshold.
possibleTableMatches
Rename candidates scoring 55–69. Shown as "needs manual review" — not auto-accepted.
summary
Counts: identical tables, changed tables, constraint changes, rename candidates, tables only in A/B. Drives the health banner and summary cards.
