CASE 1 E-Commerce

Table renames detected via FK graph — the algorithm's most powerful signal.

Version 1 · Left
ecom_v1
erDiagram users { int id PK varchar email UK varchar full_name timestamp created_at boolean is_active } categories { int id PK varchar name UK text description } products { int id PK varchar name numeric price int stock_qty int category_id FK timestamp created_at } orders { int id PK int user_id FK varchar status numeric total_amount timestamp placed_at } order_items { int id PK int order_id FK int product_id FK int quantity numeric unit_price } users ||--o{ orders : "places" categories ||--o{ products : "has" products ||--o{ order_items : "in" orders ||--o{ order_items : "contains"
Version 2 · Right
ecom_v2
erDiagram customers { int id PK varchar email UK varchar full_name timestamp created_at boolean is_active varchar phone } categories { int id PK varchar name UK text description } products { int id PK varchar name numeric price int stock_qty int category_id FK timestamp created_at numeric discount_pct } orders { int id PK int customer_id FK varchar status numeric total_amount timestamp placed_at } purchase_lines { int id PK int order_id FK int product_id FK int quantity numeric unit_price } payments { int id PK int order_id FK varchar method numeric amount timestamp paid_at } customers ||--o{ orders : "places" categories ||--o{ products : "has" products ||--o{ purchase_lines : "in" orders ||--o{ purchase_lines : "contains" orders ||--o{ payments : "paid via"

What the Algorithm Detects

🔄
users → customers — table rename. Detected because orders FK points to customers in v2 the same way it pointed to users in v1 (FK graph match).
🔄
order_items → purchase_lines — table rename. Name similarity is low, but identical FK structure (→ orders, → products) and column set push score above threshold.
✏️
orders.user_id → orders.customer_id — column rename detected inside matched table.
⚡
price / total_amount / unit_price — type widened from NUMERIC(10,2) to NUMERIC(12,2).
➕
customers.phone — new column (v2 only).
➕
products.discount_pct — new column (v2 only).
➕
payments — entirely new table in v2.
✅
categories — identical in both versions, algorithm reports no changes.

Column renames, a new constraint, a dropped table, and a possible rename candidate.

hr_v1

Version 2 · Right
hr_v2
erDiagram departments { int id PK varchar name UK varchar location numeric budget } employees { int id PK varchar first_name varchar last_name varchar work_email UK date hire_date int department_id FK numeric base_salary int manager_id FK } roles { int id PK varchar title int grade numeric min_salary numeric max_salary } employee_roles { int id PK int employee_id FK int role_id FK date assigned_at date end_date } time_off { int id PK int employee_id FK varchar request_type date start_date date end_date varchar status } departments ||--o{ employees : "employs" employees ||--o{ employees : "manages" roles ||--o{ employee_roles : "assigned via" employees ||--o{ employee_roles : "has" employees ||--o{ time_off : "submits"

What the Algorithm Detects

✏️
employees.email → work_email — column rename inside matched table.
✏️
employees.salary → base_salary — column rename inside matched table.
✏️
roles.level → grade — column rename inside matched table.
➕
employee_roles.end_date — new column (v2 only).
➕
CHECK (base_salary > 0) — new constraint on employees in v2.
❌
leave_requests — only in v1, reported as "table removed".
➕
time_off — only in v2. Algorithm may flag as possible rename of leave_requests (shared FK + date columns, different name).
✅
departments — identical in both versions, algorithm reports no changes.
CASE 3 University Enrollment

No renames — all 5 tables present in both versions. Shows deep constraint and nullability diffing.

Version 1 · Left
uni_v1
erDiagram departments { int id PK varchar name UK varchar code UK varchar faculty } professors { int id PK varchar first_name varchar last_name varchar email UK int department_id FK varchar rank } courses { int id PK varchar code UK varchar title int credits int department_id FK int professor_id FK } students { int id PK varchar student_number UK varchar first_name varchar last_name varchar email UK date enrolled_at numeric gpa } enrollments { int id PK int student_id FK int course_id FK varchar semester varchar grade date enrolled_at } departments ||--o{ professors : "employs" departments ||--o{ courses : "offers" professors ||--o{ courses : "teaches" students ||--o{ enrollments : "joins" courses ||--o{ enrollments : "has"
Version 2 · Right
uni_v2
erDiagram departments { int id PK varchar name UK varchar code UK varchar faculty } professors { int id PK varchar first_name varchar last_name varchar email UK int department_id FK varchar rank varchar office_number } courses { int id PK varchar code UK varchar title int credits int department_id FK int professor_id FK int max_capacity } students { int id PK varchar student_number UK varchar first_name varchar last_name varchar email UK date enrolled_at numeric gpa } enrollments { int id PK int student_id FK int course_id FK varchar semester varchar grade date enrolled_at } departments ||--o{ professors : "employs" departments ||--o{ courses : "offers" professors ||--o{ courses : "teaches" students ||--o{ enrollments : "joins" courses ||--o{ enrollments : "has"

What the Algorithm Detects

➕
professors.office_number — new column (v2 only).
➕
courses.max_capacity — new column (v2 only).
➕
CHECK courses.credits BETWEEN 1 AND 6 — new constraint in v2.
⚡
students.gpa — nullability changed: nullable (v1) → NOT NULL with DEFAULT 0.00 (v2).
➕
CHECK students.gpa BETWEEN 0.00 AND 4.00 — new constraint in v2.
🔗
enrollments FK on student_id — ON DELETE action changed: NO ACTION → CASCADE.
➕
UNIQUE (student_id, course_id, semester) — new unique constraint on enrollments in v2.
➕
CHECK enrollments.grade — new check restricting grades to A/B/C/D/F/W.
✅
departments — identical in both versions, algorithm reports no changes.
